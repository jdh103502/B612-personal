# 행성의 구역 분할과 무작위 생성 기술 설계안

작성일: 2026-10-29. 사용자가 요청한 기술 설계 역할에 따라 검토한 제안이다. `GameDesign.md`의 기본 기획을 전제로 하며, 아래 구조와 수치는 아직 구현되거나 확정된 규칙이 아니다.

## 첫 시제품 적용 (2026-10-30)

### 시제품 검증 결과

Unity 6000.3.23f1의 열린 에디터에서 Unity CLI로 확인했다.

아래 40개 분포 검증은 동시 상한 추가 전의 결과다. `ValidateSeeds`는 분포 회귀 검사를 위해 테스트 중에만 상한을 40으로 올리고 종료 후 복원한다. 현재 기본 플레이는 동시에 최대 6개이며 양이 먹어서 생긴 빈자리는 다음 생성 시점에 채운다.

- 일시정지: `Time.timeScale = 0`일 때 경과 시간과 생성 수가 변하지 않았다.

### 지평선 말풍선 (2026-10-30 추가)

- `SproutHorizonIndicators`는 기존 타이머 Canvas의 자식이다. 활성 싹마다 행성 Collider를 향한 시선 Raycast로 싹의 아래·중간·윗부분이 모두 가려지는지 확인한다. 일부가 직접 보이면 말풍선을 숨긴다. 다른 구조물의 가림 판정은 이번 범위에 없다.
- 플레이어의 행성 중심 방향에서 싹의 중심 방향까지 이어지는 대원 경로를 따라 표면을 조회한다. 최초로 가시 영역에서 가려진 영역으로 넘어가는 지점을 이분 탐색해 실제 지형의 지평선을 구한다. 플레이어 쪽 지면이 이미 가려진 카메라에서는 카메라 쪽 방향을 시작점으로 쓴다.

## 권장 구조

하나의 연속된 행성 표면 위에 논리적인 구역을 두고, 각 구역이 실제 생성 가능한 배치 지점들을 관리한다.

```text
행성의 메시와 지면 Collider
  └─ 논리 구역 SurfaceCell
       ├─ 구역 종류 / 이웃 / 면적 / 예약 정보
       └─ 배치 지점 SpawnSlot
            └─ 작물, 바오밥 싹, 작은 장식 등
```

구역마다 메시, Collider, MonoBehaviour를 따로 만들 필요는 없다. 구역과 지점은 우선 C# 데이터로 보관하고, 씬에서는 Gizmos로 경계와 배치 상태를 확인한다. 실제 게임 오브젝트는 지형·구조물·작물·싹에만 생성한다.

이렇게 하면 구역 경계에 보이는 틈이나 단차를 만들지 않고, 기존의 구형 중력과 이동을 유지하면서 생성 규칙을 추가할 수 있다.

## 현재 코드에서 활용할 부분과 바꿀 부분

- `AgentScripts/B612Builder.cs`의 `BuildAsteroid`는 이미 `Ico(4, ...)`를 변형해 울퉁불퉁한 행성 메시를 만든다. 저해상도 icosphere의 삼각형을 논리 구역으로 사용하는 접근과 잘 맞는다.
- 같은 파일의 `Ico`는 Editor 빌더 내부의 메시 생성 함수다. 그대로 런타임에 호출할 수 있는 구조는 아니므로, 필요한 분할·정점·면·이웃 계산을 공용 코드로 추출하거나 별도로 구현한다.
- `OnTop(x, z)`는 월드 위에서 아래로 Raycast를 쏘므로 현재의 위쪽 평지 배치에 맞춰져 있다. 행성 뒷면과 밑면까지 배치하려면 중심을 향하는 표면 조회로 바꿔야 한다.
- 현재 일부 Raycast는 모든 레이어를 조회한다. 새 배치 시스템에서는 해당 행성의 지면 Collider만 조회해 집 지붕, 작물, 다른 행성 등을 지면으로 선택하지 않게 한다.
- `GravitySource.Pull`은 행성 중심을 향하는 중력을 제공하고, `GravityWalker`는 접지 상태에서 바닥 법선을 사용한다. 이 기본 구조를 유지한다.
- `GravitySource.surfaceRadius`는 중력원 선택에 쓰는 대표 반경이다. 실제 울퉁불퉁한 표면의 위치나 최대 반경으로 간주하지 않는다.
- 씬과 `Generated/`를 다시 만드는 Editor 빌더와, 플레이 중 행성을 만드는 런타임 생성기를 구분한다. 프리팹·설정 에셋을 준비하는 일은 Editor에서, 설정에 따라 배치를 결정하는 일은 런타임에서 담당한다.

## 1. 논리 구역은 저해상도 icosphere로 만든다

정이십면체의 삼각형을 분할하고 정점을 구면에 투영한다. 면 수는 분할 0회 20개, 1회 80개, 2회 320개다.

첫 시제품은 현재 크기의 행성에 80개 구역을 제안한다. 큰 행성에서는 원하는 구역당 면적에 맞춰 320개 등을 선택한다. 표시용 고해상도 메시의 모든 삼각형을 게임 구역으로 삼지는 않는다.

선택 이유:

- 위도·경도 격자처럼 극지방에 칸이 심하게 몰리는 구조를 피할 수 있다.
- 각 삼각형의 이웃이 명확해 구역 확장과 경로 탐색이 쉽다.
- 기존 행성 메시 생성 방식과 개념을 공유할 수 있다.
- 육각형 타일의 예외 처리나 구역별 곡면 프리팹 제작부터 시작할 필요가 없다.

구역의 면적이 모두 완전히 같지는 않다. 구역 개수만으로 작물이나 싹의 수를 배분하지 않고, 구면 면적과 실제 사용 가능한 배치 지점 수를 함께 사용한다. 거친 지형의 실제 면적이 필요해지면 별도로 계산한다.

경계는 행성 로컬 공간의 단위 방향 세 개로 정의한다. 행성이 회전하거나 위치가 바뀌어도 구역 식별은 유지된다. 삼각형 내부의 방향을 구한 뒤 실제 표면으로 투영한다.

## 2. 구역 하나에 물체 하나를 강제하지 않는다

구역은 관리 단위이고, 배치 지점은 실제 위치 후보이다. 농지 구역에 작물 여러 개가 들어갈 수 있고, 집 하나가 여러 구역에 걸칠 수도 있다.

각 구역 안에서 여러 후보 방향을 만들고 다음 조건을 검사해 배치 지점을 만든다.

1. 행성 바깥에서 중심 방향으로 쏜 Raycast가 해당 지면을 맞히는가.
2. 해당 물체가 허용하는 경사와 지형 조건을 만족하는가.
3. 주변 물체의 점유 범위와 겹치지 않는가.
4. 착지 지점, NPC 상호작용 공간, 통로 등 보호 구역을 침범하지 않는가.
5. 플레이어가 도달할 수 있는 지면에 속하는가.

구역 안의 후보도 가장자리까지 사용할 수 있다. 이웃 구역의 물체와도 거리 검사를 수행한다. 현재 규모에서는 배치된 물체를 순회해 검사하는 방식으로 먼저 구현하고, 측정상 필요할 때 공간 인덱스를 추가한다.

작물은 유효한 지점 중 일부를 군집으로 선택하고 위치·회전·크기에 작은 변화를 준다. 모든 구역 정중앙에 놓는 규칙은 피한다.

### 지면 조회와 방향

- Raycast 시작점은 해당 행성의 bounds를 완전히 벗어난 지점으로 잡는다.
- `Collider.Raycast`로 행성의 지면만 조회하고 `hit.point`, `hit.normal`을 얻는다.
- 나무와 작물은 표면 법선을 위로 삼고, 그 법선을 축으로 무작위 회전을 더한다.
- 지면 경사는 법선과 월드 위쪽이 아니라, 법선과 해당 위치의 중력 반대 방향 사이의 각도로 판단한다. 행성 밑면도 평지일 수 있다.
- 집과 NPC는 허용 경사를 더 낮게 잡고, 중심과 바닥 주변을 여러 번 표본 조사해 바닥이 뜨거나 묻히는지 검사한다. 작은 행성의 곡률에 맞는 받침대나 평탄화가 필요할 수 있다.
- 첫 구현의 기본 지면은 중심에서 각 방향으로 하나의 표면이 있는 형태로 제한한다. 동굴 내부나 겹친 돌출부의 여러 바닥을 생성 위치로 쓰는 일은 이후 범위로 둔다.

## 3. 큰 구조와 필수 공간을 먼저 배치한다

제안하는 생성 순서는 다음과 같다.

1. 행성 seed, 크기, 테마, NPC와 퀘스트 조건을 결정한다.
2. 기본 지형 메시와 지면 Collider를 만든다.
3. 논리 구역을 만들고 표면 조건을 조사한다.
4. 착지 공간, NPC 공간, 출발 공간을 선택하고 필요한 통로를 예약한다.
5. 큰 바위, 언덕, 구조물 등 큰 요소를 배치한다. 지형 변경 후 예약 공간과 통로를 다시 검증한다.
6. 최종 지면에 배치 지점을 만들고, 퀘스트에 맞는 종류와 생성량 규칙으로 작물을 놓는다.
7. 작은 장식을 놓고, 바오밥 싹이 사용할 유효 지점을 확보한다.
8. 전체 배치를 검증한 뒤 플레이를 시작한다.

작물은 바오밥 폭주 전에 이미 존재해야 한다. 기본 플레이 순서가 폭주 다음에 수확이라고 해서 작물을 폭주가 끝난 뒤에 생성하면, 폭주 실패 시 작물이 죽는 규칙과 맞지 않는다.

구조물에는 모델 크기 외에 바닥 점유 범위, 출입구 방향, 상호작용 여유 공간을 정의한다. 구역 경계 밖으로 나가더라도 점유 범위 안의 모든 배치 지점을 예약한다.

통로는 예약 폭을 두고, 장식과 구조물의 실제 충돌체가 그 폭을 침범하지 않는지 검사한다. 물체가 서로 겹치지 않는다는 사실만으로 이동 가능한 행성이 되지는 않는다.

### 지형 요소의 첫 구현 범위

- 첫 단계: 몇 종류의 기본 행성 모양에 낮은 바위, 완만한 언덕, 농지 군집, 작은 구조물 등 검수한 요소를 배치한다.
- 다음 단계: 저주파 높이 변화와 완만한 분화구를 연속된 메시의 변형으로 만든다. 인접 구역 경계에서도 같은 높이 함수를 사용해 틈을 막는다.
- 별도 단계: 절벽, 깊은 골짜기, 점프 전용 지형, 동굴 등은 이동 가능성 검증을 추가한 뒤 도입한다.

지형 프리팹은 평면 바닥을 가진 임의의 모델을 작은 구면에 얹는 것만으로 완성되지 않는다. 크기 제한, 곡률에 맞는 바닥, 받침대 또는 지면 변형 중 맞는 방식을 준비해야 한다.

## 4. 접근 가능성은 별도로 검증한다

첫 시제품은 완만하고 끊기지 않은 기본 지면과 넓은 우회 공간을 전제로 한다.

- 논리 구역의 이웃 정보는 탐색 후보를 제공한다. 이웃이라고 바로 이동 가능한 것은 아니다.
- 지형 변형과 큰 구조물 배치 이후, 충분히 촘촘한 지면 표본 사이를 연결해 경사·단차·장애물·플레이어 크기를 검사한다.
- 착지 공간에서 탐색을 시작해 NPC, 출발 공간, 필수 작물의 상호작용 위치가 연결되는지 확인한다.
- 예약 통로는 연결성을 쉽게 보장하기 위한 장치이며, 최종 지형의 충돌 검사로 확인한다.
- 현재 `GravityWalker.maxGroundAngle`은 60도지만, 생성기는 더 보수적인 경사를 사용해 실제 조작 여유를 둔다. 적절한 수치는 플레이 검증으로 정한다.
- 점프를 해야만 갈 수 있는 곳은 보행 연결성과 구분한다. 첫 구현에서 필수 목표는 점프 도달 거리의 경계값에 두지 않는다.

표본 기반 연결성 검사도 연속적인 물리 이동의 완전한 증명은 아니다. 검수한 지형과 통로 폭 제한을 함께 사용하고, 자동 이동 또는 실제 플레이로 검증한다.

## 5. 바오밥 폭주는 미리 검증한 지점을 사용한다

지형과 작물은 행성 준비 중에 결정하고, 폭주 중에는 바오밥용 지점 목록에서 조건에 맞는 곳을 선택한다.

- 정적 배치 예약과 동적 점유 상태를 구분한다.
- 이미 싹이 있거나, 구조물·작물의 보호 범위 안이거나, NPC 대화 공간인 지점은 제외한다.
- 플레이어 바로 아래 생성을 막는 거리 조건 등은 별도의 조절 가능한 규칙으로 둔다.
- 폭주 시간, 생성 속도, 동시 활성 싹 수 상한은 구역 분할 수와 독립적인 값으로 둔다.
- 작은 행성에서 후보가 고갈될 수 있으므로 재시도 횟수와 대기량에 상한을 둔다. 유효하지 않은 위치에 억지로 만들지 않는다.
- 후보 부족으로 실제 생성량이 줄면 기록해 지점 밀도와 난이도 예산을 조정한다. 점유된 후보를 매 프레임 무한 재추첨하지 않는다.
- 제거된 싹은 재사용할 수 있도록 오브젝트 풀을 고려한다. 생성·제거 빈도를 측정해 적용한다.

행성 크기에 따른 수량은 우선 사용 가능한 표면적에 비례하도록 제안한다. 구형 근사에서는 면적이 `4πR²`이므로, 반경 두 배가 면적 네 배라는 차이를 밸런스 설정에 반영한다. 이는 기본 기획의 '크기에 비례'를 수치화하기 위한 제안이다.

2026-10-31 보완: 면적은 행성별 바오밥 프로필 선택의 초기 입력으로 사용하고, 회당 생성 수·동시 활성 상한·생성 간격은 별도로 설정한다. 싹 종류별 성장·배치 크기와 행성별 고정 한계량의 연결은 `BaobabThreatDesign.md`의 확장 설계를 따른다. 면적 변화나 현재 싹 수로 게임 도중 한계량을 자동 변경하지 않는다.

## 최소 데이터와 책임 분리

| 구성 | 담당 정보와 역할 |
| --- | --- |
| `PlanetDefinition` | seed, 생성기 버전, 크기, 테마, NPC·작물 조건, 생성량 설정 |
| `PlanetSurface` | 중심, 지면 Collider, 방향을 실제 표면 위치·법선으로 변환 |
| `SurfaceCell` | 안정적인 ID, 구면 경계, 이웃, 구역 성격, 면적 추정 |
| `SpawnSlot` | ID, 소속 구역, 로컬 표면 위치·법선, 허용 종류, 예약·점유 상태 |
| `PlacementRule` | 점유 크기, 허용 경사, 최소 간격, 배치 가중치, 충돌·통로 조건 |
| `PlanetGenerator` | 단계별 생성, 제한된 재시도, 최종 배치 결과 생성 |
| `BaobabDirector` | 폭주 시간과 생성 예산, 동적 후보 선택, 싹의 생명주기 |
| `GenerationValidator` | 접근 가능성, 충돌, 필수 공간, 작물 생성 규칙 검증 |

`SpawnSlot` 하나에 전부를 떠넘기지 않는다. 양 설치 가능 여부, 수확 상태, 바오밥 성장 단계는 실제 작물·싹의 게임 로직이 관리하고, 지점은 해당 오브젝트의 점유만 관리한다.

## 재현성과 실패 처리

- 지형, 구조물, 작물, 장식, 폭주는 분리된 난수 흐름을 사용한다. 장식 하나를 추가했다고 전체 게임 배치가 달라지는 일을 줄인다.
- 같은 seed와 같은 생성기 버전·설정에서 같은 결과를 목표로 한다. 물리 쿼리 순서도 안정적인 순서로 처리한다.
- 저장이 필요해지면 seed뿐 아니라 생성기 버전과 배치 결과·게임 상태를 저장할지 결정한다. 생성 알고리즘이 바뀌면 같은 seed라도 결과가 바뀔 수 있다.
- 후보 탐색과 행성 전체 재생성에는 횟수 상한을 둔다.
- 필수 공간 확보 실패 시 장식부터 줄이고, 구조물을 재배치하거나 다른 지형 변형을 시도한다. 계속 실패하면 검수한 기본 배치를 사용한다.
- 퀘스트에 맞는 작물이 생성 규칙상 누락되지 않는지 검증한다. 보유한 양·휴식·자원 때문에 모든 퀘스트를 완수할 수 있어야 하는지는 별도의 게임 밸런스 결정이다.

## 구현 순서와 완료 기준 제안

1. 기존 빈 행성에 80개 논리 구역을 표시한다. 회전·이동 후에도 구역 ID와 경계가 유지되는지 확인한다.
2. 지면 위에 배치 지점을 표시한다. 극·밑면·비평면 지형에서도 위치, 법선, 경사 판정이 맞는지 확인한다.
3. 착지·NPC·출발 공간과 구조물 하나를 예약한다. 경계를 넘는 점유와 통로가 보존되는지 확인한다.
4. 퀘스트 조건에 맞는 작물 군집을 생성한다. 수량·간격·도달 가능성을 검증한다.
5. 같은 지점 체계로 바오밥 폭주를 구현한다. 후보 고갈과 동시 활성 상한에서도 처리가 종료되는지 확인한다.
6. 여러 크기와 여러 seed를 검사하고, 실패한 seed·실패 이유·생성량·준비 시간을 기록한다.
7. 기본 루프가 검증된 뒤 지형 변형과 시각적 다양성을 늘린다.
