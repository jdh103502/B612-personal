## 1. 변경 목표와 현재 원인

사용자 요구: 행성이 커질 때 타일 하나를 크게 늘리는 대신, **타일 개수를 늘려 타일의 월드 기준 크기를 비슷하게 유지**한다.

여기서 타일은 `PlanetSurfaceGrid.SurfaceCell`인 논리 구역이다. 화면에 보이는 지형 메시의 폴리곤 수를 늘리는 요청으로 해석하지 않는다. 지형 메시·MeshCollider와 논리 구역은 계속 분리한다.

수정 전 구현에서 확인한 원인:

- `PlanetGenerationSettings.subdivisions = 1`을 모든 행성에 동일하게 적용한다.
- `PlanetSurfaceGrid.BuildCells()`는 정이십면체의 면을 재귀적으로 4분할한다. 구역 수는 `20 × 4^subdivisions`다.
- 따라서 현재 기본값은 행성 크기와 관계없이 80개다. 반지름이 2배면 평균 구역 면적은 약 4배가 된다.
- `PlanetWorldInstance.Prepare()`는 지면의 `sizeScale`은 바꾸지만 격자에는 동일한 `subdivisions`만 전달한다.
- 격자 기준 Transform은 배율 1이다. 이 Transform의 `localScale`을 읽어도 실제 행성 크기를 알 수 없다.

아래 알고리즘과 상한은 최초 구현 제안이었으며, 후속 구현 요청에서 적용한 시제품 기본값이다. 최종 밸런스나 연속적인 타일 수 증가 규칙을 확정한 것은 아니다.

## 2. 기준은 길이가 아니라 표면적이다

같은 지형을 균일 확대하는 현재 행성에서는 다음 관계가 성립한다.

```text
s = PlanetSpec.terrain.sizeScale
기준 행성 구역 수 N0 = 80
표면적 비율 = s²
이상적인 구역 수 Ntarget = N0 × s²
```

예를 들어 1.5배 행성은 약 180개, 2배 행성은 약 320개가 기준이다. 단순히 `80 × s`로 늘리면 큰 행성의 타일도 계속 커진다.

실제 지형에는 요철이 있으므로 `4πr²`를 정확한 메시 면적으로 취급하지 않는다. 현재처럼 같은 메시를 균일 확대할 때는 실제 메시 면적도 s²에 비례하므로 매번 메시의 모든 삼각형 면적을 합산할 필요가 없다. 새로운 지형 형태를 도입할 때는 템플릿별 기준 면적을 따로 검토한다.

## 3. 권장안: 정이십면체의 변 분할 수를 크기에 맞춘다

기존 재귀 분할만 사용하면 80 → 320 → 1280개로 늘어 중간 밀도를 선택하기 어렵다. **정이십면체의 각 변을 f개로 나누는 구면 삼각 격자**를 사용하면 20·80·180·320개 등을 만들 수 있다.

```text
baseFrequency = 2^baselineSubdivisions
frequency = ceil(baseFrequency × s)
cellCount = 20 × frequency²
```

- 기존 `subdivisions` 필드는 이름을 유지하고 **원본 1배 행성의 기준 분할 단계**로 해석한다. 기존 직렬화 값을 깨뜨리는 단순 필드 이름 변경을 피한다.
- 기본 `baselineSubdivisions = 1`이므로 `baseFrequency = 2`다.
- frequency는 정이십면체 원래 변의 분할 수다. 기존 `subdivisions`와 같은 숫자 개념이 아니다. `frequency = 3`을 기존 `subdivisions = 3`으로 전달하면 안 된다.
- 올림을 사용하면 이상적인 구역 수보다 같거나 많은 구역을 확보한다. **구면 기준 평균 구역 면적**이 기준 행성보다 커지는 것을 막는 선택이다.
- 삼각형 분할 수는 정수이므로 완전히 일정한 타일 크기나 연속적인 구역 수 증가를 보장하지 않는다. 아래의 단계 변화는 의도된 동작이다.

### 기본 설정의 예시

| 크기 배율 s | 이상적인 구역 수 | frequency | 실제 구역 수 | 평균 구역 면적 / 기준 평균 |
| --- | ---: | ---: | ---: | ---: |
| 0.7 | 39.2 | 2 | 80 | 0.49 |
| 1.0 | 80 | 2 | 80 | 1.00 |
| 1.25 | 125 | 3 | 180 | 약 0.69 |
| 1.5 | 180 | 3 | 180 | 1.00 |
| 1.75 | 245 | 4 | 320 | 약 0.77 |
| 2.0 | 320 | 4 | 320 | 1.00 |

평균 면적 비율은 `s² × N0 / cellCount`로 계산한다. 논리 구역은 완전한 동일 면적이 아니고 실제 지형 투영으로도 면적이 달라지므로, 개별 타일의 최대 변 길이·최대 실제 면적까지 고정하는 보장은 아니다.

### 양자화에서 알아둘 점

- 기본 설정에서는 정확히 1배까지 80개, 1배 초과~1.5배까지 180개, 1.5배 초과~2배까지 320개다.
- 1배 바로 위에서 80 → 180개로 증가하므로 그 구간의 타일은 기준보다 작아진다. '행성이 커질수록 타일도 커지는 현상 방지'를 우선한 현실적인 첫 구현이다.
- 0.7배에서 약 40개를 만들지는 않는다. frequency 1은 20개라 오히려 타일이 기준보다 커지므로 80개를 사용한다. 작은 행성까지 정확히 면적 비례 개수를 맞추는 것은 이번 안의 보장 범위가 아니다.
- 더 부드러운 구역 수 변화가 꼭 필요해지면 목표 개수를 받는 구면 분할을 별도로 검토한다. 이때는 현재 삼각형 구역·이웃·포함 판정에 미치는 영향도 함께 검토한다. 첫 구현에서 정확히 125개 등을 맞추려고 일부 삼각형만 임의로 분할하지 않는다.

## 4. 분할 결과의 데이터 계약

기존 `SurfaceCell`의 계약을 유지한다.

```text
SurfaceCell
  id              : 0부터 연속되는 활성 격자 내부 ID
  a, b, c         : 정규화된 구면 방향, 일관된 꼭짓점 순서
  solidAngle      : 해당 삼각 구역의 입체각
  neighbors[3]    : 변을 공유하는 이웃 구역 ID
  slots           : 실제 지면 Collider에 투영한 생성 후보
```

권장 생성 절차:

1. 기존 정이십면체의 12개 정점과 20개 면을 사용한다.
2. 각 원래 면 안에 변 분할 수 f의 삼각 격자를 만든다. 한 면당 f²개 삼각형이다.
3. 예: 원래 면의 단위 방향 a/b/c에 대해 `(f-i-j)·a + i·b + j·c`를 정규화해 격자 정점을 만든다. `i ≥ 0`, `j ≥ 0`, `i+j ≤ f`다.
4. 면끼리 공유하는 변의 정점은 **원래 변의 두 정점 ID와 변 위 분할 위치**를 키로 공유한다. 반대 방향에서 접근하면 분할 위치를 `f-step`으로 변환한다. 부동소수점 좌표의 문자열 비교로 정점을 합치지 않는다.
5. 삼각형 꼭짓점 순서를 바깥쪽 기준으로 일관되게 하고, 현재 `Contains`의 방향 판정과 호환시킨다.
6. 공유 정점 ID의 변 키로 이웃을 연결한다. 서로 다른 면의 경계에도 이웃이 정확히 연결되어야 한다.
7. 입체각을 계산한 뒤 기존 `TryProject`·경사 제한·후보 추출을 적용한다.

frequency가 2의 거듭제곱이면 기존 재귀 중점 분할 경로를 유지해도 된다. 특히 **원본 1배의 기존 80개 구역은 꼭짓점·면 순서까지 유지하는 안을 권장**한다. frequency 3·5 등 중간 값은 위 격자 경로로 생성한다. 두 경로의 결과는 동일한 `SurfaceCell` 계약으로 반환한다.

각 원래 면의 경계를 서로 다른 수로 나누면 틈과 이웃 누락이 생긴다. 첫 구현은 모든 원래 면에 동일한 f를 사용한다. 타일마다 GameObject·MeshCollider를 추가할 필요는 없다.

| `PlanetGenerationSettings` | 기존 `subdivisions`를 기준 행성 밀도로 유지. 크기별 구역 수를 별도로 손입력하지 않음 |
| `PlanetWorldInstance.Prepare()` | `data.spec.terrain.sizeScale`과 기준 subdivisions를 격자에 전달한 뒤 준비 |
| `PlanetSurfaceGrid` | 크기 입력, frequency 계산, 중간 분할 수 생성, 현재 준비된 해상도 조회 |
| `BaobabSurge.Begin()` | 격자를 다시 준비해도 이미 설정한 크기·frequency가 유지되는지 확인 |
| `PlanetSurfaceGrid.OnDrawGizmosSelected()` | 새 해상도와 일치하는 격자를 그림. 기존 고정 개수 검사 제거 |
| 검증 스크립트 | 무조건 80개라는 전제를 기준 배율·frequency에 맞게 수정 |

### 입력과 준비 순서

```text
PlanetWorldInstance.Prepare(planetData, settings, ...)
  지면 scale = 고정 원본 scale × sizeScale
  surface.ground = 새 지면 Collider
  surface.ConfigureResolution(settings.subdivisions, sizeScale)
  Physics.SyncTransforms()
  surface.Prepare(planetSeed)
  스폰 투영과 월드 검증

실제 도착
  Surge를 새 surface에 연결
  Surge.Begin()
    surface.Prepare(...)를 다시 호출한다면 같은 해상도 입력 사용
    cellCounts = new int[surface.Cells.Count]
```

- 크기는 `spec.terrain.sizeScale`에서 받는다. `SurfaceGrid.transform.localScale`, 지도 아이콘 크기, `GravitySource.surfaceRadius`로 역산하지 않는다.
- 기준 분할 단계·행성 배율·해석한 frequency를 하나의 준비 입력으로 취급한다. Inspector에서 최종 frequency·구역 수를 읽을 수 있게 하면 검증이 쉽다.
- `Prepare`는 생성 후보와 점유 기록을 다시 만든다. 크기 입력은 행성 진입 전에 확정하고, 플레이 도중·지도 열기·카메라 이동 때문에 재준비하지 않는다.
- 원본 기준으로 계산한다. 2배 행성 다음 0.7배 행성의 밀도가 직전 frequency를 기준으로 누적 계산되면 안 된다.

### Gizmos의 중요한 회귀 지점

수정 전 Gizmos는 `cells.Count != 20 × 4^subdivisions`이면 `BuildCells()`를 호출했다. 이 조건을 그대로 두면 정상적인 180개 격자를 잘못된 것으로 판단해 **구역·slots를 플레이 중 다시 만들어 버릴 수 있다.**

새 구현은 준비한 해상도의 구역을 그린다. Play 모드에서 Gizmos가 `BuildCells/Prepare`로 활성 격자·점유·cell ID를 변경하지 못하게 한다. Edit 모드의 미리보기 격자가 필요하면 플레이 격자와 구분하거나 준비되지 않은 상태에서만 생성한다.

## 6. 후보 지점·바오밥과의 관계

기본 후보 수는 기존처럼 **구역당 최대 32개**로 유지한다. 작은 구역의 후보를 다시 행성 배율만큼 늘리지 않는다.

- 80개 구역: 최대 2,560개 후보.
- 180개 구역: 최대 5,760개 후보.
- 320개 구역: 최대 10,240개 후보.

급경사·Collider 투영 실패로 실제 후보 수는 이보다 적을 수 있다. 기존 구역별 유한 시도 상한을 유지하고 유효 후보가 없는 구역은 생성 대상에서 제외한다.

- `BaobabSurge`의 구역별 누적 사용 배열은 최종 `Cells.Count`로 준비한다. 오래된 80칸 배열을 다음 행성에서 재사용하지 않는다.
- 구역별 생성 균형, 실제 월드 좌표의 최소 거리 1.4m, 플레이어·스폰 보호 거리를 유지한다. 구역 수 증가 때문에 간격을 배율로 키우거나 줄이지 않는다.
- **구역 증가와 바오밥 개체 수 증가는 별개**다. 이번 변경으로 생성 40회·동시 상한 6개·120초·위험도 한계 100을 자동으로 늘리지 않는다.
- 현재 방식은 구역 간 분포 균형이며 실제 지형 면적에 완벽히 비례한 생성은 아니다. 타일 밀도 변경을 이유로 면적 가중 추첨·신규 싹 종류·작물 생성까지 동시에 바꾸지 않는다.
- 기존 `Contains`, 슬롯의 로컬 점·법선, 먹기·제거 시 점유 반환, 양의 바오밥 타깃 참조가 계속 동작해야 한다.

## 7. 범위·비용·재현성

- 지원 행성 배율은 기존대로 0.7~2.0이다. NaN·무한대·범위 밖 입력은 기존 행성 데이터 검증에서 거부한다.
- 기준 subdivisions는 기존 범위 0~2를 유지한다. 이에 따른 baseFrequency는 1·2·4, 최대 2배의 frequency 상한은 8이고 최대 구역 수는 1,280개다. 기본 설정에서는 최대 320개다.
- 지원 범위를 넘는 설정은 준비 전에 오류로 처리한다. 조용히 최대 분할 수로 잘라 타일 크기 보장을 깨뜨리지 않는다.
- 격자와 후보는 행성 준비 시 계산하고 매 프레임 다시 만들지 않는다. 기준 subdivisions를 높이면 후보·Raycast 비용도 늘어난다는 점을 Inspector 도움말에 적는다.
- 같은 seed·sizeScale·기준 설정·생성기 버전은 같은 격자 순서와 후보 결과를 만들어야 한다. 원래 면 순회·변 정점 공유·삼각형 순서를 결정적으로 유지한다.
- 구역 ID는 해당 행성의 해당 격자 안에서만 유효하다. 다른 행성이나 다른 해상도의 동일한 숫자 ID를 같은 구역으로 취급하지 않는다.
- 구현할 때는 변경된 분할 알고리즘을 생성기 버전에 반영하고 새 테스트 여정으로 검증한다. 기존 데이터의 구역 ID를 새 격자에 그대로 복구하면 안 된다. 데이터 형식 버전과 생성기 버전은 구분한다.
- 구현에서는 생성기 버전 2와 데이터 형식 버전 1을 구분한다. 최초 형식 예시의 버전 1을 새 격자의 저장/복구 지원으로 해석하지 않는다. 중간 저장은 기존 명세대로 별도 범위다.

## 8. 검증 조건

### 해상도와 형상

- 기본 설정에서 위 표의 0.7/1.0/1.25/1.5/1.75/2.0 배율이 각각 80/80/180/180/320/320개다.
- 1.0·1.5의 정확한 경계, 바로 아래·위 값에서 올림 처리가 일관된다. 부동소수점 오차 대응이 필요하면 허용 오차를 명시하고 경계 테스트를 고정한다.
- 구역 ID가 연속되고 중복 삼각형·길이 0인 변·뒤집힌 면이 없다.
- 각 구역의 이웃은 서로 다른 3개이며 범위 안이고 상호 연결된다. 원래 정이십면체 면 경계에도 구멍이 없다.
- 입체각 합이 허용 오차 안에서 4π다. 삼각 격자의 정점/변 개수도 각각 `10f²+2` / `30f²`인지 확인한다.
- 구면에서 균일하게 뽑은 다수의 방향이 내부에서는 정확히 한 구역에 속한다. 공통 변 위 방향은 허용 오차 때문에 중복 포함될 수 있으므로 별도 처리한다.
- 1배의 기존 80개 구역은 가능하면 기존 순서·방향을 유지한다. 같은 seed 재준비 시 후보가 재현된다.

### 실제 씬과 전환

- 1배와 2배 행성을 같은 Gizmos 조건에서 비교하면 2배에서 구역 수가 4배가 되고 평균 타일 크기가 비슷하다.
- 2배 → 0.7배 → 1배 이동에서 구역 수·후보·점유 배열이 정상 초기화된다. 밀도가 누적되지 않는다.
- 초기 월드 준비와 `Surge.Begin`의 재준비 결과가 일치한다. 큰 행성이 바오밥 시작 순간 80개로 돌아가지 않는다.
- Play 중 Scene 뷰 선택·Gizmos 표시·지도 열기/닫기로 셀·슬롯·점유·바오밥 타깃이 바뀌지 않는다.
- 기본 동시 6개 제한과 최소 간격, 구면 전체 분포, 후보 부족 시 유한 종료, 양의 먹기·회수, 생성 종료와 게임 오버가 유지된다.
- 0.7/2배 행성에서 플레이어 이동·접지·중력·카메라가 기존처럼 동작한다. 논리 격자 변경으로 지형 메시나 Collider를 다시 만들지 않는다.
- 최대 기본 설정 320개에서 행성 준비 시간을 측정한다. 1,280개는 상한 설정 검증으로 따로 측정하고, 실제 개체 수가 적어도 후보 탐색 비용은 증가한다는 점을 확인한다.

기존 `AgentScripts/BaobabPrototypeValidation.cs`의 `Cells.Count == 80` 검사는 1배 기준 회귀 검사라면 유지할 수 있다. 임의 크기 행성 검사에서는 해석한 frequency의 예상 개수를 검증한다. 기존 검사를 단순 삭제해 새 격자의 이웃·분포 오류를 놓치지 않는다.

## 다른 구현 chat에 전달할 요청문

> `Docs/GameDesign.md`, `Docs/PlanetGenerationDesign.md`, `Docs/PlanetTileDensityImplementationSpec.md`를 읽고 행성 크기에 따라 논리 타일 수가 증가하도록 구현해줘. 기존 지형 메시·Collider는 유지하고 기본 subdivisions=1의 원본 80개를 기준으로, `frequency = ceil(2^subdivisions × sizeScale)`, `cellCount = 20 × frequency²`를 적용해줘. 기본 1배=80개·1.5배=180개·2배=320개이며, 격자 크기는 `spec.terrain.sizeScale`에서 받는다. 중간 frequency의 공유 변·이웃·포함 판정을 보장하고, Surge의 재준비와 Gizmos가 고정 80개로 되돌리거나 활성 슬롯을 재생성하지 않게 해줘. 바오밥 수량·위험도·이동 수치는 그대로 유지하고 생성기 버전·기존 검증을 함께 정리해줘. 런타임 코드 사본은 기존 프로젝트 방식에 맞게 동기화하고 실제 전환·배치 회귀를 확인해줘.
